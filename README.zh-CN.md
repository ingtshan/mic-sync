# MicSync 🎙️

[English](README.md) | **简体中文**

**一个麦克风,多台 Mac 共享。** 麦克风物理接在一台电脑(服务端)上,局域网内其他电脑(客户端)通过虚拟声卡把它当成本机麦克风使用——无需来回插拔切换。

## 需求出发点

手边有不止一台 Mac 的人,很容易撞上同一个尴尬:**好麦克风只有一支**。

- 会议今天在公司 MacBook 上开,明天在个人 Mac mini 上开,麦克风得跟着人来回插拔;USB 麦克风/声卡频繁插拔麻烦,还伤接口
- 蓝牙耳机一旦启用麦克风,音质立刻掉到"电话级"(HFP 协议),好耳机也救不回来
- macOS 自带的连续互通(Continuity)只能把 **iPhone** 当作麦克风,并不能把另一台 **Mac** 的麦克风拿过来用
- 现成的网络音频方案(NDI、Dante 等)要么偏重、要么收费,而且大多是**常驻串流**——没人说话也一直占带宽、耗 CPU

MicSync 只解决这一件小事:**让接在一台 Mac 上的麦克风,变成局域网里其他 Mac 的"本机麦克风"**。并且要"平时安静":服务端平时**完全不开麦、零流量**,客户端一键发起使用才按需开麦串流,停止使用立即关麦。

## 使用场景

- **双机位办公**:工作 MacBook + 个人台式 Mac 同一张桌子,麦克风接在其中一台;另一台要开会时,直接把会议软件的输入选成 BlackHole 即可,零插拔
- **多台 Mac 轮流开会**:同一个人先后在不同 Mac 上进会(公司环境 / 客户环境切换),坐到哪台前面就在哪台点一下「使用这个麦克风」——新请求自动接管旧串流,原设备随之停止,无需回头关闭
- **共享高品质录音链路**:电容麦 + 声卡接在录音/直播机位上,旁边的 Mac 需要临时进会时,直接借用这条链路的声音
- **不重复进声**:同一时间只有一台客户端真正收流(最新请求接管,串行轮转),不会把同一份人声同时送进两个会议

## 设备拓扑

一台**服务端 Mac**(物理麦克风所在)+ N 台**客户端 Mac**,同一局域网,星型拓扑;客户端各自安装 [BlackHole](https://existential.audio/blackhole/) 回环虚拟声卡作为"虚拟麦克风"出口:

```
                       局域网(同一网段)
                             │
             ┌───────────────┴───────────────┐
             │          服务端 Mac × 1        │
             │  🎙️ 物理麦克风(内置/USB/声卡)   │
             │  MicSync「服务端」 :47800       │
             └───────────────┬───────────────┘
   GET /health 探活          │   GET /stream(全局唯一,新请求接管)
      ┌───────────────┬──────┴────────┬───────────────┐
      │  客户端 Mac A  │  客户端 Mac B  │  客户端 Mac C   │
      │  BlackHole    │  BlackHole    │  BlackHole    │
      │  → Zoom       │  → 微信        │  → Teams      │
      └───────────────┴───────────────┴───────────────┘
          同一时间只有一台客户端持有串流(最新请求接管)
```

服务端只做 API 监听,一切由客户端请求事件驱动:**平时麦克风完全关闭、没有任何音频流量;客户端请求 `/stream` 的瞬间服务端才按需开麦**,客户端断开即关麦。新请求会接管旧串流——人在哪台设备,麦克风就跟到哪台。数据流细节:

```
┌─ 服务端 Mac ─────────────────┐         ┌─ 客户端 Mac × N ─────────────────────┐
│ 应用启动即监听 API,不开麦     │  HTTP   │ 用户点「使用这个麦克风」               │
│                              │←────────│   ↓ GET /stream(即请求事件)          │
│ 收到 /stream → 按需打开麦克风  │         │ 服务端开麦,串流建立                   │
│   ↓ cpal 采集                │  HTTP   │   ↓ 重采样 + 抖动缓冲                 │
│ PCM 16bit 单声道帧            ├────────→│ 播放到 BlackHole(回环虚拟声卡)        │
│                              │  局域网  │   ↓                                  │
│ 客户端断开 / 被新请求接管      │         │ Zoom/微信/会议软件选 "BlackHole 2ch"  │
│   → 立即关麦                  │         │ 作为麦克风 ✓                          │
└──────────────────────────────┘         └──────────────────────────────────────┘
```

## 使用方法

### 服务端(麦克风所在的电脑)

1. 打开 MicSync 即可——应用启动后自动在局域网监听,无需任何点击;需要时可在「📡 服务端」标签里换共享的麦克风设备或暂停服务
2. 把界面上显示的 `IP:端口` 告诉客户端(点击即可复制)

### 客户端(想用这个麦克风的电脑)

1. 安装 BlackHole 虚拟声卡(一次性,应用内有引导按钮):
   - **推荐**:前往官网 <https://existential.audio/blackhole/> 免费获取图形安装器(需填邮箱),下载后双击 `.pkg` 按提示安装——图形安装器会强制走完管理员授权,不会静默失败
   - 备选:`brew install blackhole-2ch`(注意:若安装过程中 sudo 授权未完成,brew 可能显示"已安装"但驱动实际没装上;可用 `ls /Library/Audio/Plug-Ins/HAL/` 核对是否存在 `BlackHole2ch.driver`)

   > ⚠️ 安装完成后需要**重启电脑**(或执行 `sudo killall coreaudiod` 重启音频服务),BlackHole 才会出现在设备列表中。
2. 打开 MicSync,切到「💻 客户端」标签
3. 填服务端地址,输出设备选 **BlackHole 2ch**,点「⚡ 自动跟随本机应用」(或手动模式的「使用这个麦克风」)
4. 在任意应用(Zoom / 微信 / 腾讯会议…)里把麦克风选为 **BlackHole 2ch**

客户端有两种模式:

- **⚡ 自动跟随(推荐,需 macOS 14+)**:开启后完全无需手动操作——MicSync 通过 CoreAudio HAL 监视 BlackHole 的使用状态,检测到本机有应用把它当麦克风采集(比如进了会议)就自动向服务端请求麦克风;应用停止采集约 2 秒后自动释放、远端关麦
- **🎙 手动使用**:点击立即请求,点「停止使用」立即释放

两种模式下,**同一时间只有一台设备在用**:另一台设备发起请求会自动接管,原设备收到通知后停止(自动跟随模式会等本轮本机使用结束后再恢复待命,不会与接管方拉锯)——人在哪台,麦克风就在哪台。网络闪断/服务端重启会自动重连。

## HTTP API

服务端在监听端口上提供两个接口(默认 `47800`):

| 接口 | 说明 |
| --- | --- |
| `GET /health` | 探活 + 状态:`{"status":"ok","app":"micsync","streaming":false,"client":"","sample_rate":48000}` |
| `GET /stream` | 请求使用麦克风(即事件):服务端按需开麦,返回 `200`(`application/octet-stream`,正文为 `MSY1` 头 + 长度前缀 PCM 帧)。已有串流时**新请求接管**,旧连接收到 0 长度结束帧(附原因码:被接管/服务端停止);开麦失败返回 `503` |

## 技术要点

- **Tauri 2** + 纯静态前端(无 Node 依赖)
- **cpal** 做音频采集/播放(CoreAudio)
- 极简 HTTP 服务(std 手写,无框架):`/health` 探活 + `/stream` 串流,流正文为 `MSY1` 魔数头 + 长度前缀 PCM i16 帧,`TCP_NODELAY` 低延迟
- **按需开麦**:服务端启动只监听 API,不碰麦克风;每次 `/stream` 会话独占一条 cpal 采集流,会话结束(断开/被接管)立即释放——系统的麦克风指示灯只在真正使用时亮起
- **自动跟随检测**(客户端):待命期查 BlackHole 设备的 `kAudioDevicePropertyDeviceIsRunningSomewhere`(此时客户端不持有任何流,它变 true 即「有应用开始用虚拟麦克风」);收流期自己在播放、该属性恒 true,改查 macOS 14+ 的 Process Objects API(`kAudioHardwarePropertyProcessObjectList`,即系统橙色麦克风指示灯的数据源)判断「除本进程外是否仍有进程在采集」。轮询本机 HAL 属性,单次约 3ms,300ms 一查
- **抢占式单串流**:同一时间只有一条串流;新请求接管旧串流,旧客户端收到明确的结束帧后停止(不自动抢回,避免设备间来回拉锯)
- 客户端 60ms 起播水位 + 300ms 缓冲上限(超限丢旧数据保延迟),流式线性重采样兼容任意采样率组合
- 串流期间带宽约 0.8 Mbps(48kHz · 16bit · 单声道);无人使用时零音频流量、零麦克风占用
- 虚拟麦克风由 [BlackHole](https://github.com/ExistentialAudio/BlackHole) 回环驱动提供;自研 CoreAudio HAL 驱动(免装 BlackHole)列为后续方向

## 已知限制 / 后续方向

- 发起使用到出声之间有开麦初始化(通常 <1s)+ 60ms 起播水位的一次性延迟;建立后为持续低延迟串流
- 自动跟随的「结束」信号只能近似:其他进程用哪个设备采集因隐私不可见(`pdv#` 返回空),故本机若还有别的应用在采集任意麦克风(如听写),远端麦克风会保持占用直到它也停止
- 接管是无条件的(局域网内任何客户端都可接管),未做加密/鉴权,请仅在可信局域网使用
- 后续可选:Opus 压缩(跨网段/弱网)、mDNS 自动发现服务端、自研 HAL 驱动
